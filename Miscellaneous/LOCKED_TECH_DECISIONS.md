# Glimpses — Locked Technology Decisions

**What this file is:** the finalized answer to every ruled `T-nn`, kept **tight and reference-grade** — what to build, named precisely, nothing more. The technology-phase counterpart of `LOCKED_PRODUCT.md`, but deliberately without its reasoning bullets.

**What this file is not:** the explanation. It does not teach the concept, walk through alternatives, or justify the choice — that lives in **`TECH_EXPLANATIONS.md`**, linked by the same `T-nn`. This file is what you read to know what Glimpses runs on; that file is what you read to understand why and how it works.

**Source of truth for:** stack, runtime, service shapes, data model, naming. **Source of truth for product behaviour remains `LOCKED_PRODUCT.md`** — if a technology entry here ever implies different product behaviour than a `P-nn`, the `P-nn` wins and this entry is wrong.

**Covers:** all 8 agenda areas ruled — technology phase closed. **Opened:** 2026-08-06.

## 1. Runtime and language

**`T-01` — All Python.** Every Lambda — API handlers and the HEIC→JPEG conversion alike — runs on Python/boto3. Consolidated routing (multiple endpoints per Lambda) via AWS Lambda Powertools' `APIGatewayRestResolver`, which also handles API Gateway response conversion natively. No middleware engine (middy has no Python equivalent and Powertools already covers routing/response/CORS). No DynamoDB Toolbox (TS-only; not needed under a multi-table, GSI-per-access-pattern data model) — plain typed wrapper functions over `boto3`/`DocumentClient` cover data access instead. Layering follows `handler → manager → procedure/converter → DAO`, a folder convention independent of language.

## 2. Ingestion orchestration

**`T-02` — Step Functions Distributed Map**, not SQS + DLQ, for the face-indexing fan-out step of ingestion. The Map state iterates the batch's photo list — supplied via an **S3 `ItemReader`** pointed at the extraction step's output folder, never as a JSON array passed between states — invoking the indexing Lambda per photo up to a configured concurrency ceiling. Retry-with-backoff and a tolerated-failure-percentage are declared on the state itself; the state's completion is the batch's completion, with no separate polling loop or DynamoDB "is it done" counter required.

**`MaxConcurrency` is a Terraform variable** (e.g. `rekognition_index_max_concurrency`), not a hardcoded value — it must be set to the deploying account's actual Rekognition `IndexFaces` TPS Service Quota (check via the Service Quotas console; new/lightly-used accounts commonly start below the published default of 50 TPS). Document this requirement plainly in the Terraform variable description and in Sam-facing deploy docs, since a mismatch here produces silent throttling, not a build failure.

**`MatchOneAttendee`** (ruled 2026-08-16, follow-up to this section) — a second entry point into `ingestion`, alongside the batch-arrival `MatchAttendees` fan-out, closing the gap where an attendee admitted/joined/rejoined after an event's last batch never gets (re-)matched. Triggered by a DynamoDB Stream on `EventAttendees` (`NEW_AND_OLD_IMAGES`), filtered to `OldImage.status != "ATTENDEE" AND NewImage.status == "ATTENDEE"`, via a Lambda Event Source Mapping on `ingestion` — not a direct `Membership` invoke, so `Membership` stays unaware matching exists. Runs one `SearchFaces` call for that one attendee against the event's full collection, reusing `MatchAttendees`' own match-resolution logic. Full reasoning and rejected alternatives in `TECH_EXPLANATIONS.md` §2.

**Pipeline (Step Functions-triggered, `T-02`) — one consolidated Lambda, `ingestion`** *(renamed 2026-08-13, previously `PipelineHandler`; `InitializeJob` moved out to `db-api` the same day, see follow-up row below)***:** five Step-Functions-driven steps — `Extract` (unzip, dedup, format-sniff, HEIC convert, thumbnail, write to S3/`Photos`, plus a manifest of the batch's photos to `uploads/.../manifest.json`) → `IndexOnePhoto` (one per photo, invoked by the Distributed Map via an S3 `ItemReader` on that manifest; Rekognition `IndexFaces`) → `Finalize` (tallies the batch, computes terminal outcome and storage total) → `ListAttendees` (queries `EventAttendees`' `eventID-status-index` for the event's currently-`ATTENDEE` roster — added 2026-08-17, closing a real gap: nothing else in the pipeline ever enumerated who `MatchAttendees`' fan-out should run against) → `MatchAttendees` (Distributed Map, per-attendee `SearchFaces` fan-out, items supplied inline via the prior step's output — `P-93`'s 100-attendee/event target stays well under the state-transfer limit, so no `ItemReader` needed here) — each state invoking the same physical Lambda, passing a `step` field in its input; the handler branches internally. **Plus a sixth entry point, `MatchOneAttendee`, invoked outside Step Functions entirely** — by a DynamoDB Stream Event Source Mapping on `EventAttendees`, not by any state machine or external caller (see `MatchOneAttendee` below `T-02`). **Shared utility, each called from multiple places:** HEIC→JPEG converter (called from `Extract` and `Profile`, per `P-35`). `db-api` — a generic `Jobs`-table writer, called as its own state from **five** points in the ingestion state machine: `InitializeJob` (creates the `Jobs` row, moved in from the pipeline Lambda 2026-08-13) plus the four status updates (`EXTRACTING`, `INDEXING`, the terminal outcome, `FAILED`); deliberately a separate Lambda rather than a shared code library, so the write is reusable and visible in the state machine's execution history — accepted tradeoff: a `db-api` failure after a real step has already succeeded can abort a batch whose work is done, which a same-process library call would not risk. Handler branches on an `action` field (`create` vs `update_status`).

**API Gateway flavour: REST API** (ruled 2026-08-09, follow-up to this section) — over HTTP API, specifically for AWS WAF support against Rohan's named adversarial threat model (`P-07`), accepting REST API's $3.50/million-request cost over HTTP API's $1/million. Confirms `T-01`'s `APIGatewayRestResolver` was correct as written.

**`CascadeDelete`** (ruled 2026-08-09 as `EventTeardown`, follow-up to this section, surfaced while ruling `T-04`'s `Events` schema; **renamed and widened 2026-08-12**, surfaced while ruling `T-04`'s `Faces` schema) — a 9th Lambda, not API-facing, IAM-scoped to `Events`, `Photos`, `Faces`, `EventAttendees`, S3, and the Rekognition collection API. The one Lambda in the system trusted with any multi-table delete cascade. Invoked three ways: directly by the `Events` Lambda's delete endpoint (`P-34`, organizer-triggered, whole-event cascade), by a DynamoDB Stream on `Events` reacting to a TTL-expired item (the automatic 60-day delete, `P-77`, whole-event cascade), and directly by `Gallery/photos`' delete endpoint (`P-44`/`P-52`, single/bulk-photo cascade — `DeleteFaces`, `Faces` row deletion, `Events` counter decrement). Deliberately kept as one Lambda rather than widening the caller's own role (`Events` in 2026-08-09's ruling, `Gallery/photos` in 2026-08-12's) or building a second near-duplicate cascade Lambda for the photo case — both would either give back or duplicate the one-table IAM isolation `T-04` was built for.

**`Jobs`** (ruled 2026-08-12, follow-up to this section) — PK = `jobId`, no SK, one GSI: `eventUploaderKey` (`"{eventID}#{uploaderID}"`, PK) + `startedAt` (SK), so an uploader can find their own latest job in an event without carrying a `jobId` forward, per `P-100`. **`status` enum, locked 2026-08-17, revised 2026-08-18 (`PARTIAL` dropped, enum ownership moved into `db_api`):** `CREATED` (written by `InitializeJob` at row creation) → `EXTRACTING` → `INDEXING` → `MATCHING` → one of `SUCCESS`/`FAILED` (two-way terminal outcome, decided by a `Choice` state right after `Finalize` reading `succeededCount`: zero succeeded routes straight to `JobFailed`, skipping `ListAttendees`/`MatchAttendees` entirely since there's nothing new for them to match against; any nonzero count proceeds through matching to an unconditional `mark_success`). `FAILED` is also reachable from any in-progress status via `JobFailed`, on any execution-level error, not only the zero-succeeded case. **The state machine no longer sends literal status strings to `db_api` at all** — it calls named actions (`mark_extracting`/`mark_indexing`/`mark_matching`/`mark_success`/`mark_failed`), and `db_api`'s own `Manager` owns the action→status-string mapping and rejects any unrecognized action; this is the actual enum-enforcement boundary, not the ASL. **`MATCHING` is a technology-layer call, not a product ruling** — nothing in `LOCKED_PRODUCT.md` requires phase-accurate job status; it exists so the row doesn't sit stuck on a stale `INDEXING` value for however long the attendee-matching Distributed Map runs (throttled by Rekognition's `SearchFacesByImage` TPS quota, same shape as `IndexPhotos`), confirmed with the user directly rather than assumed.

**`Photos`** (ruled 2026-08-12, follow-up to this section) — PK = `photoID`, no SK. GSI 1: `eventID` (PK) + `"{uploadedAt}#{filename}"` (SK), the gallery/cursor-pagination index (`P-57`/`P-63`/`P-16`). GSI 2: `eventID` (PK) + `contentHash` (SK), the dedup check (`P-38`). `displayName`/`email` attribution snapshotted at upload time per `P-99`; `sizeBytes` stored per row for `P-85`'s atomic storage counter on `Events`.

**`EventAttendees`** (ruled 2026-08-12, follow-up to this section) — PK = `userID`, SK = `eventID`. Fields: `status` (`PENDING`/`ATTENDEE`/`LEFT`/`BLOCKED`), `matchedPhotoIDs` (String Set). Row is never deleted — leave and eject/deny are status flips on the same row. One GSI: `eventID` (PK) + `status` (SK), serving the roster/lobby (`P-82`/`P-83`) and `MatchAttendees`' own "who's admitted" lookup. `CascadeDelete` does not scrub `matchedPhotoIDs` on photo delete — stale ids are filtered out for free at read time.

**`download`** (ruled 2026-08-15, follow-up to this section, surfaced scoping the endpoint-path gap) — a 10th Lambda, not API-facing on any table but its own, IAM-scoped to `Downloads` (read/write, new table, see §4) + `Photos` (read-only) + S3 (read photos bucket, write downloads prefix). Owns `POST /events/{eventId}/photos/download` (kickoff, async invoke) and `GET /events/{eventId}/downloads/{downloadId}/status` (poll). Built as a plain asynchronous Lambda invocation, not a Step Functions state machine — this is one sequential job (stream S3 objects into a zip, `STORED` method, multipart-upload back to S3), with no Rekognition throttle to coordinate across items, unlike `T-02`'s fan-out. At `P-93`'s 1,000-photo/event scale, estimated build time is a few minutes, well inside Lambda's 15-minute cap — comfortably faster than API Gateway's 29s synchronous limit would allow, which is why this couldn't just be a synchronous `Gallery/photos` endpoint. `Gallery/photos` keeps the non-zip download path (`POST /events/{eventId}/photos/download-urls`, pre-signed URLs, no server processing) — only the zip case needed a dedicated Lambda + table.

## 4. Data model

**`T-04` — Multi-table, not single-table design.** Seven DynamoDB tables *(amended 2026-08-15 from 6 — `Downloads` added, see below)*, each scoped to one entity type, each keyed by that entity's own natural id: `Users` (`userID`), `Events` (`eventID`), `Jobs` (`jobId`), `Photos` (`photoID`), `Faces` (`rekognitionFaceID`), `EventAttendees` (`userID`+`eventID`), `Downloads` (`downloadId`). Cross-entity reads are ordinary `get`/`batchGet`/GSI-`query` calls across separate tables — no shared key space, no item collections. **Drops v1's `SearchRateLimit` table entirely** — `P-16` removed search as a user action, so there is nothing left for it to rate-limit. GSI-per-named-access-pattern discipline carries over from v1 unchanged. **Per-table field lists, PK/SK choices beyond the primary id, and GSI definitions are now fully ruled for all 7 tables** — see the `T-03` follow-up rulings above for `Jobs`/`Photos`/`EventAttendees`/`CascadeDelete`/`download`, and `TECH_EXPLANATIONS.md`'s `T-04` follow-up section for the full reasoning on every table, including `Users`, `Events`, and `Faces`.

**`Downloads`** (ruled 2026-08-15, follow-up to this section) — PK = `downloadId`, no SK. Fields: `downloadId`, `eventID`, `requesterID`, `status` (`PENDING`/`READY`/`FAILED`), `s3Key` (set once ready), `createdAt`. **No GSI** — deliberately, unlike `Jobs`' `eventUploaderKey` GSI: no product ruling requires a zip download to survive a closed tab/dead session the way `P-100` requires for uploads, so the requester just holds the `downloadId` returned synchronously from the kickoff call. S3 objects under the downloads prefix get a lifecycle-expiry rule (default 48h, adjustable) — same class of "stored artifact needing a lifecycle" as `P-90`'s QR image.

## 5. Rekognition collection lifecycle

**`T-05` — One Rekognition collection per event.** Created by application code at event creation (`create_event`), never in Terraform, since a collection is a data-dependent runtime resource tied to a specific `eventID` — Terraform has no visibility into it. `IndexOnePhoto` indexes each photo's faces into that event's own collection; `SearchFaces` for an attendee only ever queries that one collection, so `P-07`'s no-cross-event-visibility rule is enforced by AWS itself, not application-code filtering. `P-32` archiving is a single `DeleteCollection` call. The collection's id is stored on the `Events` table (`rekognitionCollectionID`) so a teardown script can enumerate and delete orphaned collections without depending on Terraform state. `P-52`'s per-photo deletion still requires retaining each photo's face-vector IDs so `DeleteFaces` can target them specifically, independent of this ruling.

## 6. Terraform state and naming

**`T-06` — State backend: S3 bucket, native S3 locking (`use_lockfile = true`, Terraform ≥1.10), no DynamoDB, versioning on.** No local state, ever, past the very first bootstrap. `terraform.tfstate*` stays gitignored — state files hold real values in plaintext regardless of `sensitive` markings.

**Module layout:** each of the 10 Lambdas (`T-03`) is `Backend/<name>/` (code) + `Backend/<name>/infra/` (a self-contained child module): `lambda.tf`, `iam_role.tf`, `iam_policies.tf`, `cloudwatch.tf`, `input.tf`, `output.tf`. Root `/infrastructure` is the composition root — `imports.tf` (one `module` block per Lambda + shared modules `api_gateway`, `dynamodb`, `state_machines`), `providers.tf`, `variables.tf`, `outputs.tf`.

**Deploy discipline:** every Lambda's own Jenkinsfile runs `terraform apply -target=module.<lambda>` then its code push (GitHub → zip → deployment-artifacts S3 bucket → `aws lambda update-function-code`). Every `lambda.tf` carries `lifecycle { ignore_changes = [s3_key, source_code_hash] }`. **Five separate, dedicated CI jobs**, belonging to no single Lambda, cover the cross-module resources: `dynamodb` (untargeted apply of the `dynamodb` module only), `buckets` (untargeted apply of the `buckets` module only — creates `glimpses-deploy-artifacts` and `glimpses-photos`), `alarms` (untargeted apply of the `alarms` module only — creates the shared operator-alerts SNS topic), `cloudfront` (targeted apply of the `cloudfront` module only — depends on `buckets`' outputs for its origin and bucket policy), and `state_machines` (untargeted apply of the `state_machines` module only) *(amended 2026-08-15, adding `buckets`/`alarms`/`cloudfront` as the shared-infrastructure modules those three Lambdas needed to actually wire into root `imports.tf`; the earlier two-job split into `dynamodb`/`state_machines` was Rewritten 2026-08-13, see the `T-06` follow-up row above)*, since the state machine's Terraform embeds each Lambda's ARN and cannot apply until all 10 Lambda jobs already have, and `cloudfront` cannot apply until `buckets` already has. Each new shared module deliberately keeps its own Jenkinsfile rather than being folded into one bundled job — kept separate for understandability, per the user's explicit call, even though `dynamodb`/`buckets`/`alarms` could technically share one untargeted apply. **Fixed run order: `dynamodb` / `buckets` / `alarms` (mutually independent, any order) → `cloudfront` → all 10 per-Lambda jobs → `state_machines`.** None run automatically — all are run by hand, in that order, whenever module wiring changes.

**CI/CD granularity: 15 jobs total** *(amended 2026-08-15 from 12, adding `buckets`/`alarms`/`cloudfront` as dedicated jobs for the shared-infrastructure modules; amended 2026-08-15 from 11 before that, following `download`'s addition as a 10th Lambda; amended 2026-08-13 from 10 before that, splitting the combined untargeted-apply job into `dynamodb` and `state_machines`; amended 2026-08-09 from 9 before that, following `CascadeDelete`'s addition as `EventTeardown`)* — 10 per-Lambda Jenkinsfiles + `dynamodb` + `buckets` + `alarms` + `cloudfront` + `state_machines`. ## 7. Observability, IAM, CORS, secrets

**`T-07` — ruled 2026-08-09, four sub-decisions.**

**Logging:** Powertools `Logger`, structured JSON, on all 10 Lambdas *(ruled at 8; `CascadeDelete` and `download` each inherit the same treatment, no separate ruling needed)* — no new dependency, since `T-01` already ships Powertools. `log_event=True`: the full incoming request is auto-logged on every invocation (chosen deliberately over selective-field-only logging). CloudWatch log retention set to **3 days** on every Lambda's log group, a direct consequence of `log_event=True` capturing sensitive request data (e.g. the `P-19` profile selfie).

**Tracing:** no X-Ray / Powertools `Tracer`. Cross-Lambda correlation relies on structured log fields (e.g. `jobID`) instead.

**Metrics:** no custom Powertools `Metrics`. AWS's default Lambda metrics (`Errors`, `Duration`, `Invocations`, `Throttles`) only — `P-100`'s tolerated-failure-percentage stays a manual read of Step Functions execution history, not an alarmable number.

**Alarms:** every alarm wired to an **SNS topic with an email subscription** — closes v1's silent-alarm bug (`HANDOFF.md` §7: alarms existed, nothing was ever subscribed). Alarm content: `Errors > 0` over a 5-minute window, identical shape on all 10 Lambdas, living in each Lambda's own `cloudwatch.tf` per `T-06`'s per-Lambda module layout — which also structurally closes v1's hardcoded-alarm-list bug (a new Lambda's alarm ships with its module, not a separately-remembered central list). `P-81` bounds all of this to operator-only notification; nothing here is ever user-facing.

**IAM granularity:** strict one-role-per-Lambda (unchanged shape from `T-03`/`T-04`'s table-scoped roles), but each Lambda's permission list is **derived from a per-Lambda manifest of its actual AWS calls**, not hand-guessed upfront — closing `HANDOFF.md` §7's "permission missing, discovered only at runtime" gap by construction rather than by hoping nothing was forgotten.

**CORS:** restricted to the real frontend origin(s) via a Terraform variable (v1's own `app_urls`, never wired through — now actually connected), not `*`. `localhost` (or whatever local dev origin is used) must be included in the allowed list for local frontend development against a deployed backend.

**Secrets:** a pre-commit secret scanner (**`gitleaks`**) added from the repository's first commit, blocking any commit containing AWS-key-shaped or PEM-shaped content before it reaches history — the direct fix for `HANDOFF.md` §6's committed CloudFront private key and plaintext AWS-key incidents.

## 8. Testing approach and CI/CD

**`T-08` — ruled 2026-08-09, seven sub-decisions.**

**Pyramid shape:** 3-tier — unit → integration → E2E, matching v1's own shape.

**Unit tests:** `pytest` + `moto` (fakes AWS in-memory, no network, no Docker), matching v1.

**Explicit failure-path tests required, not just happy-path coverage:**
- Corrupted ZIP drives the pipeline to `FAILED`
- One deliberately-bad photo in a Distributed Map batch fails only that item; the execution still completes; the per-item failure appears in the Distributed Map's S3 result output *(adapted from v1's DLQ/`COMPLETE_WITH_ERRORS` test — `T-02` has no DLQ)* — verified by code review only, not a live test, same accepted compromise as v1
- Direct S3 GET on a private object fails
- Expired signed URL fails
- Unauthenticated calls get 401, cross-role calls get 403
- Each Lambda's IAM policy matches its manifest of actual AWS calls (new, closes `T-07`'s manifest against silent drift)

**Integration tests:** scoped to one Lambda's full internal chain (`handler → manager → service/dao`) invoked as a single unit, `moto`-backed at the AWS boundary. No cross-Lambda test chaining — Step Functions already guarantees state-to-state handoff shape.

**E2E tests:** run against a dedicated test `Event` (with its own real Rekognition collection and a few real photos), created and torn down by the test itself, inside the project's single AWS account. **Manual only** — not wired into any Jenkins job, to control real Rekognition spend.

**CI/CD wiring:** tests are **not** part of any of the 9 Jenkins jobs (`T-06`). The developer runs unit + integration tests locally and only pushes to trigger a Jenkins deploy once local tests pass — Jenkins is a pure deploy mechanism, not a test gate. The dedicated untargeted-apply job stays independent and manual, unchanged from `T-06`.

**Coverage:** no formal coverage threshold or tool (`pytest-cov` not adopted). The explicit failure-path list above is the actual substance; coverage percentage isn't tracked as a separate metric.

## 9. S3 bucket/key layout, CDN, and ingestion trigger

**`T-09` — ruled 2026-08-15, closes gaps 2 and 3 surfaced building `heic_converter`.**

**One S3 bucket, `glimpses-photos`, six top-level prefixes** — not one bucket per category. Prefix-level scoping (bucket policy `Resource` ARNs, S3 lifecycle rules, EventBridge key-prefix filters) gives every isolation guarantee a separate bucket would, at a fraction of the Terraform footprint.

| Prefix | Key shape | Written by | Read by |
|---|---|---|---|
| `uploads/` | `uploads/event/{eventID}/user/{userId}/job/{jobId}/original.zip` | Browser, pre-signed `PUT` (`Upload/status`) | `ingestion`'s `Extract` step, via its own IAM role (`GetObject`) |
| `photos/` | `photos/event/{eventID}/{photoID}.jpg` | `ingestion`'s `Extract` step | Browser, via CloudFront |
| `thumbnails/` | `thumbnails/event/{eventID}/{photoID}.jpg` | `ingestion`'s `Extract` step | Browser, via CloudFront |
| `selfies/` | `selfies/user/{userId}/selfie.jpg` | Browser, pre-signed `PUT` (`Profile`) | Rekognition calls (`IndexOnePhoto`/`MatchAttendees`), via IAM; **and** the owning user's own browser, via a pre-signed `GET` `Profile` mints for `GET /profile` (`Profile` derives `userId` from the authenticated caller, so it can only ever sign that caller's own key) |
| `qrcodes/` | `qrcodes/event/{eventID}/qrcode.png` | `Events`, at event creation | Browser, via CloudFront (`P-90`) |
| `downloads/` | `downloads/event/{eventID}/{downloadId}.zip` | `download` Lambda | Browser, via a pre-signed `GET` returned from the status-poll endpoint |

Every object key is fully server-determined — a pre-signed URL fixes the exact key it signs, so no client-supplied filename ever reaches S3; a fixed filename (`original.zip`, `selfie.jpg`, `qrcode.png`) is used at the leaf of every key for this reason.

**CloudFront + Origin Access Control (OAC).** `photos/`, `thumbnails/`, `qrcodes/` are served through a CloudFront distribution in front of the bucket — repeatedly-viewed, many-viewer assets, matching `P-90`'s explicit "served through CloudFront like any other asset." The bucket itself has all public access blocked; CloudFront reaches it only via OAC, and the bucket policy grants that OAC identity `s3:GetObject` on exactly those three prefixes. **`uploads/`, `selfies/`, `downloads/` are never granted** — not merely unlinked, but actively unreachable through CloudFront even if a valid-looking path is guessed, since S3 itself rejects the OAC's request outside its granted `Resource` ARNs. This is the real enforcement boundary — the prefix naming is a convention for humans, the bucket policy's `Resource` scoping is what a misconfiguration can't accidentally bypass.

**Selfies are additionally excluded from CloudFront for a product reason, not just a technical one:** `P-15`/`P-82` — profile selfies are invisible to everyone, including the organizer. Nothing outside Rekognition's own calls and the owning user's own pre-signed `GET` may ever read one.

**Selfie caching.** Since `Profile`'s `GET /profile` mints a fresh pre-signed `GET` (a new query-string signature) on every call, the URL itself isn't stable across requests — browser caching is achieved instead via `Cache-Control: private, max-age=86400` metadata set on the selfie object at upload time (honored on any successful fetch regardless of which signed URL retrieved it), paired with a pre-signed expiry at least as long as that `max-age` so the signature doesn't go stale before the cache would naturally re-fetch. `private` (not `public`) — no intermediate cache besides the requesting browser's own may ever store it.

**Ingestion trigger: S3 Event Notification → EventBridge → `StartExecution`, not a client "upload complete" callback.** The bucket has `send object events to EventBridge` enabled (all object-created events, account-wide default bus). One EventBridge Rule matches `source: aws.s3`, `detail-type: Object Created`, bucket `glimpses-photos`, key `{prefix: "uploads/"}` **and** `{suffix: "/original.zip"}` (the suffix check is defense-in-depth — every pre-signed URL for a raw upload already signs exactly this filename, so nothing else is ever written under `uploads/`). The rule's target is the `ingestion` state machine's ARN; a dedicated IAM role (assumable only by `events.amazonaws.com`) grants the rule `states:StartExecution` on that one state machine ARN. No Lambda sits between S3 and Step Functions — EventBridge targets Step Functions directly.

**Rejected: an explicit client "upload complete" callback endpoint.** Fails `P-100`'s core requirement outright — if the browser's tab closes (or network drops) between the `PUT` finishing and the callback firing, the batch never starts and `P-81` means nobody is ever told. An S3 Event Notification has no such dependency: S3 itself is the witness that the object landed, independent of whether anyone is still watching.

**Multi-file selections are client-side zipped before upload.** `P-37` makes a multi-file selection one batch, and the trigger design requires one S3 object → one `StartExecution` — so whether the user picks a ZIP or a multi-file selection, the browser always produces exactly one object at `uploads/.../original.zip` (client-side zipping, e.g. `JSZip`, for the multi-file case). `Extract`'s "unzip" step is therefore unconditional, not ZIP-only-when-present.

**What `Extract` receives.** EventBridge passes the matched S3 event's own JSON (bucket, key, size) as `StartExecution`'s input. `Extract` recovers `eventID` (and `userId`/`jobId`, though it already has `jobId` via `db-api`'s status-update calls) directly from the key — no `Jobs` table read needed just to route the event.

**Not yet decided, flagged for a future pass, not blocking:** whether to add a `retry_policy`/`dead_letter_config` on the EventBridge target for the rare case `StartExecution` itself fails transiently (EventBridge drops a failed delivery by default, unlike `T-02`'s Distributed Map which already has built-in per-item retry). Low-probability given `StartExecution` is a lightweight call, but the same failure *shape* as `HANDOFF.md` §7's silent-alarm history if left unaddressed.
