## Phase 7 — Upload flow (done, 2026-08-27)

- `src/lib/uploadApi.js` — `getUploadUrl(eventId)` (`POST /events/{eventId}/upload-url`), `getJobStatus(eventId, jobId)` (`GET .../jobs/{jobId}/status`), matching `Miscellaneous/BACKEND.md`'s `upload_status` section exactly (single presigned-PUT-URL response shape, `Jobs.status` enum).
- `src/pages/app/UploadFlow.jsx` — new route `/app/events/:eventId/upload`, translated from `Glimpses.dc.html`'s `isUpload` screen state block. One hidden `<input type="file" multiple accept="image/*,.zip,application/zip">` behind a single "Choose files" control (matches the design — there's no separate picker UI for the two paths in the mock itself). Selection logic: exactly one `.zip` file → PUT it directly, no cap; anything else → enforce the 500-photo cap (`Miscellaneous/FRONTEND.md`'s Upload flow section) client-side before doing anything, then zip via JSZip.
- `Gallery.jsx`'s header "Add" button (deliberately omitted in Phase 6) and the plain-empty-event "Add photos" CTA are both wired now, navigating to the new route.
- **Real decisions made and flagged before coding, per the task's explicit call-out (not decided silently):**
  - **Progress bar is real, not the design's fake `setInterval` simulation.** Three real phases feed one bar: "Packing" (JSZip's `generateAsync` progress callback, multi-photo path only), "Uploading" (`axios.put`'s `onUploadProgress`, byte-accurate), then discrete checkpoints once job-status polling starts (`CREATED`→10%, `EXTRACTING`→35%, `INDEXING`→65%, `MATCHING`→85%, `SUCCESS`→100%) since the backend doesn't expose a real percentage mid-job — coarse but honest rather than inventing a smooth animation.
  - **Errors are fully generic, matching the flat-502 constraint precedent from Phases 3–5.** One error state ("Something went wrong" / "Nothing you've already added was lost") covers a 502 from minting the upload URL, a failed S3 PUT, a `FAILED` job status, and a 502 mid-poll — no per-case messaging, no smart resume. "Try again" always resets back to the file picker rather than attempting to resume the specific failed step, since distinguishing failure causes isn't possible with the current backend error shape.
  - **Job-status polling via React Query**, `refetchInterval` returning `2500` while `status` isn't `SUCCESS`/`FAILED`, `false` once it is — same poll-until-done shape the phase description called for, reused as-is for Phase 8's download-status polling.
- Verified via a one-off Playwright script (scratchpad-only; `playwright` + chromium reinstalled fresh to this session's scratchpad, not a project dependency) against the dev server, with a **stateful** job-status mock (advances `CREATED → EXTRACTING → INDEXING → MATCHING → SUCCESS` one step per poll, matching the full mock API origin, not a bare path glob) and the same fake-Cognito-session-in-localStorage seeding as Phases 3–6. Exercised: multi-photo path (3 files) → "Packing your photos" (zip progress) → "Uploading" (byte progress) → processing stages appear as the mock advances → terminal `SUCCESS` renders the real `succeededCount`/`failedCount` (28 added, 2 could not be processed) → "See the gallery" returns to the gallery screen → bring-your-own-zip path (single `.zip` file) skips the zipping phase entirely and goes straight to uploading → 501-file selection is rejected client-side with the 500-photo-cap toast before any zip/network work happens → a mocked 502 from `upload-url` shows the generic error state → "Try again" resets cleanly back to "No files chosen yet". Zero unexpected console errors (only the deliberately-mocked 502 from the error-path test).

## Phase 2 — Auth (done, 2026-08-26)

- `src/lib/cognito.js` — thin promisified wrapper over `amazon-cognito-identity-js` (SRP): `signUp`, `confirmSignUp`, `resendConfirmationCode`, `login`, `forgotPassword`, `confirmPassword`, `signOut`, plus `getCurrentSession`/`refreshCurrentSession` (the latter two used by the axios interceptor). Token storage is the SDK's default `localStorage`, matching FRONTEND.md's Auth section — no custom storage adapter needed.
- `src/context/AuthContext.jsx` — `AuthProvider`/`useAuth()`, hydrates `user` (`sub`/`email`/`name` decoded from the ID token) from any cached session on mount; exposes the Cognito operations above plus `isAuthenticated`/`loading`.
- `src/lib/api.js` — axios instance (`baseURL` from `VITE_API_BASE_URL`); request interceptor attaches `Authorization: Bearer <idToken>` via `getCurrentSession()` (which the SDK auto-refreshes on a stale access token); response interceptor does an explicit `refreshCurrentSession()` + one retry on a `401`, otherwise rejects. Not yet consumed by any screen — Phase 3+ domains will import this.
- `src/components/auth/RequireAuth.jsx` — redirects to `/login` (with `location` in nav state for post-login return) when unauthenticated; wraps two new guarded placeholder routes, `/app` and `/app/profile`, standing in for the real Phase 3/4 destinations the verify-success screen links to.
- Screens (`src/pages/auth/`): `Signup`, `Login`, `VerifyCode`, `ForgotPassword`, `ResetPassword` — translated line-for-line from `Glimpses.dc.html`'s `isSignup`/`isLogin`/`isVerify` (`verifyDone`/`verifyOpen`/`codeErr`)/`isForgot`/`isReset` states, including the exact password-strength logic (4-segment meter, weak/almost-there/strong labels, missing-requirement hint) and the tap-keypad code entry (`1`–`9`, `0`, `⌫`, in that order — confirmed against the source, not guessed). `react-hook-form` for the field-based forms (signup/login/forgot/reset); the code screen uses local state since it's a custom keypad, not a text field.
- `src/components/auth/AuthShell.jsx` — shared wordmark+heading wrapper for the two screens that have it (signup, login only — verify/forgot/reset don't, per the design); takes a `pt` prop since signup's top padding (56px) differs from login's (64px) in the source file.

Without this the app fails at runtime with `ReferenceError: global is not defined`, not at build time (`npm run build` succeeds either way; only `npm run dev`/the browser console surfaces it) — worth remembering if this trips up a future dependency too.
- `.env.example` added (`VITE_COGNITO_USER_POOL_ID`, `VITE_COGNITO_CLIENT_ID`, `VITE_API_BASE_URL`) — names weren't specified in FRONTEND.md, chosen now since Phase 11's Jenkins job needs to write these from `terraform output`. A local-only `.env.local` (gitignored via the existing `*.local` pattern) has placeholder non-real values for dev-server testing.
- Verified via a one-off Playwright script (same pattern as Phase 1: playwright + chromium in the scratchpad only, not a project dependency) with the real Cognito network calls intercepted and mocked (`cognito-idp.*.amazonaws.com`, responses keyed off the `X-Amz-Target` header) so the actual app code (routing, state, error paths) runs end-to-end without hitting AWS: signup form validation (weak/mismatched → strong/matching, pixel-matched against the design after letting the 200ms color transition settle), verify-code wrong-code error state, verify-code success → `verifyDone` view, login screen, forgot → reset navigation carrying `email` through router state, and the `/app` route guard redirecting an unauthenticated visit to `/login`.
