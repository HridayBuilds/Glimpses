## Phase 10 — Polish pass (done, 2026-08-27)

- **Audit, not a rebuild** — every screen from Phases 1–9 was read in full and checked against the three FRONTEND.md line items (error states, loading/empty states, responsive layout) rather than assuming any screen needed work.
- **Loading states**: every query-driven screen already had one from its original phase (even where it was just a bare "Loading…" line) — nothing missing here.
- **Empty states**: all already present and correct (Home's "haven't created/joined an event yet", Gallery's `emptyMine`/`emptyEvent` variants, Roster's "No attendees yet.") — nothing missing here either.
- **Error states — two real gaps found and fixed**: `Home.jsx`'s `getOrganizedEvents`/`getMyEvents` queries and `Roster.jsx`'s `getAttendees` (PENDING/ATTENDEE) queries had no `isError` handling at all — a 502 left those sections silently blank (Home) or showing a misleading "Admitted: 0" (Roster) with zero indication anything had failed. Both now show the same inline "Couldn't load X. Try again shortly." pattern already established in Profile/EventEntry/Gallery from earlier phases (Roster's "No attendees yet." empty-state line is also now gated on `!errorAttendees` so it can't render during a failure).
- **Real decision, flagged before coding: kept the existing lightweight inline-message pattern rather than adopting the design's separate full-screen `isError` mockup** (centered icon + "Something went wrong" + My events/Try again buttons). That full-screen treatment isn't used anywhere else in the app even where 502s are already handled well (Profile, Gallery, EventEntry all use the inline form), so introducing it only for these two would have been inconsistent rather than a genuine fix.
- **Responsive layout: audited every app screen (auth, profile, home, create/join, event entry/lobby, roster, gallery, multi-select bar, photo viewer, upload, roster danger zone) at 1280px and 390px via a Playwright script (scratchpad-only) that checked for real horizontal overflow, not just eyeballing.** Zero overflow and zero layout breakage found anywhere — every screen already used fluid `mx-auto max-w-[Npx]` containers with flex-wrap/grid internals (never fixed pixel widths), so they degrade to phone width correctly by construction. This matches Gallery's existing `sm:` breakpoint for tile size (104px → 150px), which already mirrors the design's `wide`/narrow tile-size split. **No responsive fixes were needed** — confirmed by testing rather than assumed from the code reading alone.
- Verified via two one-off Playwright scripts (scratchpad-only; `playwright` + chromium installed fresh to this session's scratchpad, not a project dependency) against the dev server, matched on the full mock API origin. First script screenshotted all 12 static-route screens (login/signup/forgot-password/home/create-event/join-event/event-lobby-pending/gallery/roster/upload/profile/privacy) at both viewports and checked `scrollWidth` vs `clientWidth` for overflow plus filtered console errors. Second script drove Gallery into multi-select mode (bottom bar with Select all/Delete/Download ZIP) and opened the full-screen photo viewer, screenshotting both at both viewports. Zero overflow, zero unexpected console errors (only the same deliberately-fake `example.invalid` thumbnail 404s present in every prior phase's test) across all 26 screen/viewport combinations. `npm run build` also verified clean.

## Phase 8 — Download flow (done, 2026-08-27)

- `src/lib/downloadApi.js` — `requestDownload(eventId, photoIds)` (`POST /events/{eventId}/photos/download`, `photoIds` omitted for "download everything") and `getDownloadStatus(eventId, downloadId)` (`GET .../downloads/{downloadId}/status`), for the `download` Lambda's async server-side ZIP flow. `galleryApi.js` extended with `getDownloadUrls(eventId, photoIDs)` (`POST .../photos/download-urls`), for the `gallery` Lambda's direct-presigned-URL flow.
- **Real decision, flagged before coding (not decided silently): which route for which selection size.** The design mock itself already answers this — `PhotoViewer`'s header has its own `downloadOne` button, separate from the multi-select bar's `zipSelected` button. So: the photo viewer's new `Download` button uses the fast `gallery` direct-presigned-URL route (single photo, no polling needed); `Gallery.jsx`'s multi-select bar gets the design's `Download ZIP` button, wired to the `download` Lambda's async build-and-poll route (`state.zip`/`zipPct` → real `null`/`'building'`/`'ready'` state, poll-until-done via React Query, same `refetchInterval` pattern as Phase 7's job-status polling). Using the ZIP route for one photo would mean a pointless few seconds of "building" for a file that doesn't need packing.
- **Second decision, flagged before coding: no fake progress percentage.** The design's mock simulates a smooth `zipPct` via a local `setInterval`, but the real `downloads/{downloadId}/status` endpoint only ever returns `PENDING`/`READY`/`FAILED` — no numeric progress field. Per the same "coarse but honest, don't invent a smooth animation" call made in Phase 7's upload flow, the building state shows an indeterminate spinner + "Preparing download…" rather than a fake incrementing bar.
- `Gallery.jsx` — new `zipCard` banner above the grid (translated from `Glimpses.dc.html`'s `zipCard`/`zipBuilding`/`zipReady` block: spinner + "Preparing download…" while building, "Download ready" + `Dismiss`/`Download ZIP` buttons once ready), and the select bar gains the design's `Download ZIP` button (`Delete` still deliberately omitted — Phase 9). Clicking `Download ZIP` with a selection kicks off a ZIP of just those photos; the banner and the select-bar button share the same `zip` state so either surface can trigger/observe it. `PhotoViewer.jsx` gains a `Download` header button (previously omitted per Phase 6's note) wired to the direct-URL route.
- **Real bug found and fixed via testing, not just flagged: `window.open()` after an `await` gets blocked by the browser's popup blocker**, since the async gap breaks the click's user-gesture association. Both download paths now open a blank tab **synchronously** inside the click handler (before any `await`), then set that tab's `location.href` once the presigned URL resolves (`tab.close()` if the request fails) — confirmed via Playwright that a naive `await getUrl(); window.open(url)` produces a `chrome-error://chromewebdata/` dead tab, while the fixed version fires the real request in the popup.
- Errors: same generic flat-502 pattern as every other phase — a failed `POST .../photos/download` or a `FAILED` status clears the zip card back to idle and shows a toast, no per-case messaging or resume.
- Verified via a one-off Playwright script (scratchpad-only; `playwright` + chromium installed fresh to this session's scratchpad) against the dev server, matched on the full mock API origin, with a **stateful** download-status mock (`PENDING` for the first two polls, `READY` on the third, matching the poll-until-done pattern actually being exercised) and the same fake-Cognito-session-in-localStorage seeding as prior phases. Exercised: opening a photo in the viewer and clicking `Download` fires `POST .../photos/download-urls` and opens the real presigned URL in a new tab → entering select mode, picking 3 photos, and clicking `Download ZIP` shows "Preparing download…" → after polling resolves, the banner and select-bar button both flip to the ready state → clicking `Download ZIP` opens the real ZIP presigned URL in a new tab, dismisses the banner, and exits select mode → a mocked 502 from the kickoff route shows the generic error toast and clears the banner. Zero unexpected console errors (only the deliberately-fake `example.invalid` image-host DNS failures already present in every prior phase's test, plus the one deliberately-mocked 502).
