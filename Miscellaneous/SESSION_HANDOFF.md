**`CascadeDelete` — built and finished 2026-08-24, same session as `gallery`.** The 10th and last Lambda. Two dispatch actions plus a stream entry point, all sharing one cascade-order `Manager`:

- **`delete_event`** (whole-event teardown, `P-34`, also the target of the `Events` TTL Stream below): `DeleteCollection` on the event's Rekognition collection (destroys every indexed face in one call, so no per-face `DeleteFaces` is needed here) → query+batch-delete every `Faces` row for the event → query every `Photos` row, batch-delete the `photos/`+`thumbnails/` S3 objects, batch-delete the `Photos` rows → query+batch-delete every `EventAttendees` row for the event → delete the `Events` row itself. **Ruling this session ("Point 1 -> A"):** whole-event cascade delete *does* delete `EventAttendees` rows — a deliberate, scoped exception to the general "`EventAttendees` rows are never deleted" rule (`T-04`), which only holds for the leave/block/eject lifecycle a live event still has; once the event itself is gone there's nothing left for those rows to track.
- **`delete_photos`** (single/bulk photo delete, `P-44`/`P-52`, called by `gallery`): per photo — query that photo's `Faces` rows, conditionally call `DeleteFaces` on the still-live collection only if any exist (selective removal, unlike whole-event teardown), batch-delete the `Faces` rows, collect its `photos/`+`thumbnails/` S3 keys, delete the `Photos` row — then, once every photo in the batch is done, one batched `decrement_event_counters` call against `Events.photoCount`/`storageBytes` (same `ADD`-expression shape `ingestion`'s `increment_event_counters` already uses, negated; `lastUploadAt` is left untouched, since that's an ingestion-only activity signal per `P-78`).
- **`Events` TTL Stream entry point** (`P-77`'s 60-day auto-delete, previously missing from Terraform entirely): a DynamoDB Stream `event_source_mapping` on `Events`, filtered via `filter_criteria` to `eventName = REMOVE` **and** `userIdentity.type = Service`/`principalId = dynamodb.amazonaws.com` — the signature AWS stamps on a TTL-driven delete but never on an application `DeleteItem`. This is what stops `delete_event`'s own `delete_event_row` call from re-triggering itself in a loop through the same stream (identical self-trigger guard shape to `MatchOneAttendee`'s existing filter on `EventAttendees`). On a genuine TTL fire, the stream record's `OldImage.eventID` is read and passed straight into the same `delete_event_cascade` function the direct-invoke path uses.
- **Idempotency:** a missing target row (`Events`/`Photos` already gone) returns a no-op success, not an error — covers a manual delete racing the TTL sweep, or a duplicate async invoke, matching the `P-56`/`P-100` tolerated-failure precedent.
- **Gallery fix found and closed the same session (ruling: "Point 2 -> yes fixing it"):** `gallery`'s `delete_photo`/`bulk_delete_photos` never checked `Events.status` before authorizing a delete — an ARCHIVED event should deny every write including the organizer's own (`P-32`), but the old code only fetched `Events` lazily on the organizer-fallback path, so an uploader deleting their own photo on an archived event slipped through unchecked. Fixed: both paths now unconditionally fetch and status-check the event before any authorization decision. `gallery`'s tests grew from 20 to 23 (both delete paths now assert the archived-event rejection).
- **Testing:** moto does not implement any Rekognition collection API (`create_collection`/`delete_collection`/`delete_faces` all raise `NotImplementedError` under `@mock_aws`, confirmed directly) — so, matching `ingestion`'s existing precedent for `IndexFaces`/`SearchFacesByImage`, every Rekognition call is monkeypatched at the `Manager`-module level in tests, not moto-mocked. 14 tests passing (`test/unit/` + `test/integration/`).
- **IAM**, narrowly scoped to the DAO's actual calls (`T-07`): `Events` (`GetItem`/`DeleteItem` + stream-read actions), `Photos` (`GetItem`/`DeleteItem`/`BatchWriteItem`/`Query`), `Faces` (`Query`/`BatchWriteItem`), `EventAttendees` (`Query`/`BatchWriteItem`), S3 `DeleteObject` on `photos/*`/`thumbnails/*` only, Rekognition `DeleteCollection`/`DeleteFaces` (`resources = ["*"]`, no resource-level scoping exists for these actions). `table.batch_writer()`'s `BatchWriteItem` calls specifically needed calling out — a batch delete via that helper needs `dynamodb:BatchWriteItem` granted, not just `DeleteItem`.
- **Terraform:** new module `Backend/CascadeDelete/infra` wired into `infrastructure/imports.tf`; `events`' and `gallery`'s previously-empty `cascade_delete_function_name`/`cascade_delete_function_arn` variables now resolve to this module's real outputs, so their already-existing conditional IAM policies (`count = var.cascade_delete_function_arn == "" ? 0 : 1`) now actually create the `lambda:InvokeFunction` grants. `terraform fmt -recursive`/`init`/`validate` all clean (`AWS_PROFILE=glimpses`, run by the user).

**Nothing left to build except infrastructure that spans every Lambda rather than belonging to one:** the API Gateway REST API itself (`T-03`: REST over HTTP API, specifically for AWS WAF support against `P-07`'s adversarial threat model) that will front all 5 API-facing Lambdas via Powertools' `APIGatewayRestResolver`, plus the Cognito User Pool/App Client (config ruled 2026-08-23, not yet built). No Terraform for API Gateway or Cognito exists yet — both are locked rulings, not code. After that: a real `terraform apply`/Jenkins pass to actually deploy everything, which hasn't happened at all yet outside the one-time bootstrap.

## `state_machine` module and the `Jobs.status` enum — the actual live thread

Built 2026-08-17 (`infrastructure/modules/state_machine/`, ASL in `templates/ingestion_pipeline.asl.json.tftpl`, `QueryLanguage: JSONata` per the user's explicit request — rewritten from an initial JSONPath draft; both Distributed Maps' `MaxConcurrency` come from measured Rekognition quotas, both **5** on this account). Wires `Extract → IndexPhotos (Map) → Finalize → ListAttendees → MatchAttendees (Map)` end to end, triggered by an EventBridge rule on the `uploads/.../original.zip` S3 event per `T-09`.

Building/reviewing this ASL surfaced and closed, over several rounds of the user catching real gaps (not decided silently):

- `db_api` needed calling from `Jobs`' actual touch points, not just once — closed by adding a write before/after every real phase transition.
- `ListAttendees`/`MatchAttendees` had `Retry` but no `Catch` — fixed, routed to a tracked `IngestionFailed` terminal.
- The happy path had no explicit success marker — added `IngestionSucceeded` (`Type: Succeed`), symmetric with `IngestionFailed` (`Type: Fail`).
- `Extract`'s photo list was returned as a plain JSON field, contradicting `T-02`'s "never as a JSON array passed between states" — fixed to write a `manifest.json` to S3 and return only a pointer, read via a real `ItemReader`.

**Finalized 2026-08-18, this session — the enum itself and where it's enforced:**

- **Dropped `PARTIAL` entirely.** The user's call: `succeededCount`/`failedCount` already carry that nuance; a third terminal status added nothing actionable.
- **Zero-succeeded now also terminates as `FAILED`**, not any success variant.
- **Enum enforcement moved into `db_api`, out of the state machine — the user's explicit, direct instruction** ("the state machine should not tell the string that is a wrong practice"). The ASL now sends only **named actions** (`mark_extracting`/`mark_indexing`/`mark_matching`/`mark_success`/`mark_failed`/`create`); `db_api`'s `Manager` holds the one `_STATUS_BY_ACTION` mapping from action → status string, and an unrecognized action raises. This is now the actual enum-enforcement boundary.
- **`Finalize` no longer computes or returns any `status` field** — just `succeededCount`/`failedCount`. Reversed my own earlier recommendation (keep a computed status in Python) after the user asked "why do we need this status then?" — agreed it was unnecessary indirection once only one trivial check remained.
- **New `Choice` state, `CheckIndexingOutcome`, right after `Finalize`** — `succeededCount = 0` routes straight to `JobFailed`, skipping `ListAttendees`/`MatchAttendees` entirely (nothing new to match). This placement was **the user's own insight**, not mine — I'd originally proposed checking at the end of the pipeline; the user pointed out checking right after `Finalize` avoids running two states pointlessly when there's nothing to match.
- **The real terminal write moved to after `MatchAttendees`' Map**, immediately before `IngestionSucceeded` — a new unconditional `UpdateJobStatus` state calling `mark_success`, since that Map is the pipeline's actual end, not `Finalize`.

**Final `Jobs.status` enum:** `CREATED → EXTRACTING → INDEXING → MATCHING → SUCCESS`/`FAILED` (14 states total in the ASL). Fully implemented and tested — `db_api`'s `Manager`/tests updated, `ingestion`'s `finalize.py`/tests updated, ASL template updated, `LOCKED_TECH_DECISIONS.md`'s `Jobs` entry and decision log updated to match. Verified via local template render (correct state graph) plus `terraform fmt -check -recursive`/`terraform validate`, both clean.
